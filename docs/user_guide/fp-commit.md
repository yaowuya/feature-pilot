# fp-commit 用户指南

`fp-commit` 用于当前 Git 分支的代码审查、修复、验证与提交。普通模式在入口一次性选择完整执行方案，后续不重复询问已选项。显式 `auto` 模式会推送并创建 PR/MR，**不会自动合并**。

## 使用前提

当前应用需要在 `fp-docs/settings/backend.md` 或 `frontend.md` 的 `Code Standards` 中登记可用的内置规范或项目规范来源。只有 `fp-docs/manifest.md`、占位值、`Unknown`，或 `none` 且没有项目来源时，不算已初始化。技能会停止并提示运行 `/fp-init`，不会替你写入 settings。

Django、Vue 规范正文保留在插件中。项目专属规范可由 `/fp-init` 逐文件批准创建 `fp-docs/settings/code-standards.md`，并在适用端的 `Project rule sources` 中登记。已有 settings 的修改需要确认精确 diff；跳过专属文档不影响已登记内置规范的 review，但若本次发现确实需要沉淀的新规则，必须先完成专属文档登记。

## 普通模式

运行 `/fp-commit`，或要求 FeaturePilot“提交代码”。技能先读取当前分支和改动范围，再一次收齐适用选项，而不是先提交、后问推送：

| 选项 | 选择内容 |
| --- | --- |
| 模式 | 普通模式，或本轮显式选择 `auto`。 |
| 执行终点 | 仅本地提交、提交并推送，或提交并推送后创建 PR/MR。 |
| 推送目的地 | 需要推送时，确认 remote、实际推送仓库与当前 topic 分支。 |
| PR/MR 目标 | 需要创建请求时，确认同一仓库及目标分支。 |
| 合并意向 | 不合并，或检查通过后再申请最终合并。 |

原生问答支持时，缺少的选项放在同一份表单中；否则用一条消息集中展示。你已明确的选项会直接复用，不重复询问。例如：“提交并推送到 origin，在同一仓库创建目标为 release 的 PR，不合并。”技能解析并核实对应仓库与分支后执行，不会再分别问一次是否推送、是否创建 PR。

选定方案后，技能检查规范偏差与可复现的缺陷，修复并验证范围内问题，再精确暂存、提交并执行已授权的后续步骤。每个阶段仍核验真实状态，展示提交 SHA 和结果，但不把展示变成重复审批。选择仅本地提交时，远端相关选项记为 N/A，不需要远端查询或 PR/MR 鉴权；未选的阶段不执行。

入口的合并意向不等于最终合并授权。真正合并前仍须核对当前检查、冲突和保护规则，并取得明确确认。目的地、源/目标分支或变更范围发生变化时，技能会停止并只重新确认变化项；规范初始化、必要验证缺口和宿主工具权限也不因入口选择而被跳过。

## 显式 auto 模式

运行 `/fp-commit auto`。技能不再展示普通模式问卷，而是使用固定方案：review、必要修复、验证、commit、push，以及向**实际推送目的地的默认分支**创建 PR/MR，且不合并。它先解析有效 push remote、pushurl 和 URL rewriting，再向唯一的实际 push URL 查询远端 HEAD；fetch 地址与 push 地址不同时，不能混用两个仓库。它不根据本地分支名称猜 `main` 或 `master`。创建请求后立即停止，不执行 merge，也不启用平台 auto-merge。

`auto` 不是 Claude/Codex/Cursor 的权限模式，不能绕过宿主工具审批。规范未初始化、必要验证失败、改动范围不明、默认分支无法核实、远端能力不可用或请求冲突时，技能会停下说明已完成的步骤，不以猜测代替确认。

## 规范沉淀与结果

只有明确项目约定或多个独立源码/测试证据支持的新规则，才会写入**已存在且已登记**的项目规范文档，标注规则 ID、appRoot、适用端和依据。单个文件的偶然写法只是候选，不会变成全项目或插件通用规则。`fp-commit` 不能创建规范文件、改写登记或修改插件内置 Django/Vue 规则。

每次结果分别说明本轮选项、规范状态、review 与修复、测试及未验证项、实际提交和推送状态、PR/MR 链接与目标，以及是否真正合并。创建 PR/MR 不等于 CI 通过或已合并。命令本身不是 Git Hook；手工 Git 操作不会被它自动拦截。
