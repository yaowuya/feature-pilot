# fp-db-adapter 分组逐项检查设计

## 目标

调整 `fp-db-adapter` 的只读扫描与方案输出流程。Skill 触发后，应先自动识别适配模式和数据库范围，再按固定分组逐项检查。每项必须显示检查结果、证据和处置结论，让用户清楚知道检查了什么、哪些内容已适配、哪些内容需要修改。

本次设计保留现有两阶段门禁：第一阶段只读扫描并输出完整方案；用户统一确认后，第二阶段才允许修改代码。

## 核心决策

- 一次完成全部分组的只读检查，不在分组之间暂停。
- 每个检查项即时输出固定状态、证据和结论。
- 所有分组检查完成后，统一汇总未适配项并生成详细方案。
- 用户只需对完整方案进行一次明确确认。
- 实施阶段沿用检查项编号，逐项报告执行和验证进度。
- 同时支持达梦和 OceanBase，并自动判断单库或全量数据库范围。
- 自动判断全新适配或增量适配，不依赖用户预先指定。

## 工作流

### 第一阶段：只读检查与方案

1. 识别项目根目录、技术栈和关键配置入口。
2. 自动判断适配模式：全新适配或增量适配。
3. 自动判断数据库范围：达梦、OceanBase 或全部。
4. 按固定分组逐项检查，每项输出状态、证据和处理结论。
5. 汇总所有需要适配、待验证和无法判断的项目。
6. 为需要处理的项目生成可执行的详细适配方案。
7. 输出检查统计、适配模式、数据库范围、风险和实施顺序。
8. 停止并等待用户对完整方案进行统一确认。

第一阶段禁止编辑业务代码、配置、依赖、Migration、部署文件或测试文件。

### 第二阶段：实施与验证

仅在用户明确确认当前完整方案后进入：

1. 按分组和检查项编号实施。
2. 每完成或跳过一项，立即输出进度和结果。
3. 若实际代码与方案存在实质偏差，停止实施、更新方案并重新请求确认。
4. 按既有 L1-L6 验证层级执行适用的检查。
5. 输出最终适配总结、变更文件、验证结果和残余风险。

## 固定检查分组

1. 项目与适配模式识别
2. Python 及系统依赖
3. 数据库驱动与后端适配
4. 数据库连接配置
5. Migration 兼容机制
6. 现有 Migration 文件
7. ORM 查询与原生 SQL
8. 初始化、升级及运维脚本
9. 部署、镜像与环境配置
10. 测试和验证能力

分组顺序固定，便于不同项目之间比较检查结果。某个分组不适用于当前项目时，也必须保留该分组并明确输出跳过原因。

## 检查项状态

每个检查项只能使用以下状态之一：

- `[已适配，跳过]`：已有充分证据证明目标能力已适配。可见文案必须包含“`xxx 已适配，跳过`”。
- `[需要适配]`：确认缺少适配或当前实现不兼容，纳入适配方案。
- `[待验证]`：静态扫描无法证明兼容，或存在高风险，纳入验证方案。
- `[不适用，跳过]`：不属于当前项目、适配模式或数据库范围，说明原因后跳过。
- `[无法判断]`：缺少必要代码、配置或环境信息，列出需要补充的信息。

不能仅凭文件名、注释或依赖声明判断“已适配”。结论必须有可定位证据；证据不足时使用“待验证”或“无法判断”。

## 单项输出结构

每个检查项至少包含：

- 检查项编号和名称
- 固定状态
- 面向用户的明确结论
- 文件路径和当前行号（存在文件证据时）
- 稳定代码锚点（存在代码证据时）
- 判断依据或扫描发现
- 后续处置：跳过、纳入适配方案、纳入验证方案或等待信息

示例：

```markdown
### 3. 数据库驱动与后端适配

- [已适配，跳过] 3.1 达梦数据库驱动已适配，跳过
  - 证据：requirements/base.txt:42
  - 锚点：dmPython==2.5.5
  - 结论：无需修改

- [需要适配] 3.2 OceanBase 数据库后端尚未适配
  - 证据：settings/database.py:86
  - 锚点：DATABASE_ENGINES = {
  - 发现：仅存在 MySQL 和达梦配置分支
  - 处置：纳入适配方案
```

## 详细方案要求

每个 `[需要适配]` 和 `[待验证]` 项目必须在统一方案中说明：

- 检查项编号、所属分组和目标数据库
- 问题描述及判断依据
- 文件路径
- 当前行号
- 稳定代码锚点
- 当前代码或配置
- 计划修改后的代码、配置或逻辑
- 影响范围和风险
- 验证方法
- 执行顺序和前后依赖

行号反映本次扫描时的位置；实施时必须以稳定锚点和代码语义重新定位，不能只按行号修改。

`[无法判断]` 项目必须集中列出阻塞信息。如果该信息会影响方案正确性，则不能请求实施确认；应先补齐信息并完成检查。

## 汇总与确认门禁

第一阶段结束时必须输出：

- 检查项总数
- 已适配并跳过数量
- 需要适配数量
- 待验证数量
- 不适用并跳过数量
- 无法判断数量
- 自动识别的适配模式
- 自动识别的数据库范围
- 方案执行顺序
- 明确的“等待用户确认方案”状态

只有用户在看到完整方案后明确表达同意，才视为有效确认。对扫描、继续分析或补充信息的同意，不等同于实施确认。

## 实施进度

第二阶段必须复用第一阶段的编号，逐项输出进展，例如：

```text
[3.2 实施中] OceanBase 数据库后端配置
[3.2 已完成] OceanBase 数据库后端配置
[5.3 验证失败] Migration 字段类型转换
```

已适配和不适用项目不得重复修改。最终总结需要将每个计划项映射到实际变更和验证结果。

## 异常与方案漂移

- 若扫描中发现项目结构异常，先记录为“无法判断”，不得猜测并直接修改。
- 若实施时文件、锚点或行为与确认方案不一致，应判断是否构成实质方案漂移。
- 新增修改文件、扩大数据库范围、改变兼容策略或引入新依赖均属于实质漂移，必须停止并重新确认。
- 纯行号变化、等价格式调整或锚点位置移动不构成实质漂移，但应在最终总结中说明。

## 验收标准

- Skill 明确要求按十个分组逐项检查。
- 每个项目使用固定状态，并输出证据和处置结论。
- 已适配项明确显示“xxx 已适配，跳过”。
- 未适配项进入包含文件、行号、锚点、当前代码、计划代码、风险和验证的详细方案。
- 一次完成只读检查，检查结束后仅请求一次统一确认。
- 未确认前不修改项目文件。
- 实施阶段复用检查编号并逐项报告结果。
- 达梦和 OceanBase 的单库及全量范围均遵循同一流程。
