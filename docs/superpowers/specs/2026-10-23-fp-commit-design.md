# fp-commit 技能设计

**日期：** 2026-10-23

## 目标与边界

增加公开 `fp-commit` 技能，在用户要求提交代码时先执行规范门禁、代码审查、必要修复与验证，再处理提交和推送。普通模式单独询问 PR/MR 与最终合并；用户显式选择 `fp-commit auto` 时，不逐步询问，完成推送和向远端默认分支创建 PR/MR 后停止，绝不自动合并。实现本技能本身不授权当前插件仓库的提交、推送或合并。

本技能处理当前分支的指定改动，不取代 `fp-final-review` 的完整变更归档门禁。复用共享工程质量契约及已登记代码规范，不另写第二套 Django/Vue 规则。

## 入口与模式

- `commands/fp-commit.md` 仅将参数转发到 `skills/fp-commit/SKILL.md`。Codex、Cursor 和其他运行时通过同名技能与 `AGENTS.md` 路由发现。
- 未指定模式时为普通模式；仅本轮明确输入 `auto` 才进入自动模式。宿主 Agent 的权限模式、过去的选择和项目配置都不能替用户开启本轮 `auto`。`auto` 不绕过宿主工具权限。
- 普通模式可只完成本地 review、修复、验证和 commit，不以远端配置或 PR/MR 鉴权作为本地提交前提。用户选择远端阶段后，显示准确的文件范围、实际推送目的地与分支，在推送及创建 PR/MR 前分别确认；如用户选择合并，必须依据当前检查与冲突状态另获最终合并授权。
- 自动模式在预检通过后依次审查、修复、验证、提交、推送、创建 PR/MR；不逐步询问，也不执行最终合并。任何步骤缺少必要证据、规范初始化、验证、远端或目标分支时停止并报告，不猜测或降级。

## 规范初始化与项目规则

1. 从仓库根的 `fp-docs/manifest.md` 开始，按改动涉及的端/应用读取 `settings/backend.md` 或 `settings/frontend.md` 的 `Code Standards`。有效初始化要求当前 appRoot 有已验证的 Django/Vue preset，或有明确可读的项目规范来源；`Unknown`、占位值及仅有 `none` 而无项目来源不算已初始化。未满足时停止并引导 `/fp-init`；自动模式也不能代替用户批准初始化。
2. 读取插件的 `engineering-quality.md`、已登记公共/端规则、`Project rule sources` 和 `Confirmed overrides`。只对本次改动及受影响调用链审查；客户明确规范和当前用户指令优先。
3. `fp-init` 可按逐文件批准创建 `fp-docs/settings/code-standards.md` 作为项目规则正文，并将其相对路径登记进适用设置的 `Project rule sources`。默认 `manifest-only` 不创建该文件；已有 settings 的登记变更仍需精确 diff 批准。规则按 appRoot/端标注范围，不能把某应用的规范推广到全仓。
4. `fp-commit` 只维护**已存在且已登记**的专用项目规则文档，不创建/重登记 settings 或修改插件通用规则。发现新规则时先核对显式项目约定或多个独立源码/测试证据，检查重复、冲突与适用范围，再以规则 ID、陈述、适用范围、依据写入；单个偶然写法不是规范。无新规则不写文件。证据不足的候选只报告，不阻塞已验证代码；已经确认的新规范如果缺少已登记且可写的文档，则普通模式回到 `/fp-init`，自动模式停止，不带着未沉淀规则提交。

## 审查、提交与远端

- 先核对工作树、暂存区、当前分支、上游远端及改动范围。包括新增/未跟踪文件，但只纳入本次用户授权范围；排除凭据、原型本地资产、CodeGraph 索引与不相关改动。默认分支上不得直接推送并伪造 PR。
- 按公共规范的双轨方式分别报告规范偏差和有证据的代码缺陷。发现可修复问题时按当前范围修复并运行相关检查；影响范围外或无法验证的阻塞问题停止。自动模式不能通过省略必要验证来绕过确认。
- 只暂存本次文件，检查最终 staged stat、完整 diff 和 `git diff --cached --check`；快照变化后重审并重跑必要验证。无可提交改动不创建空 commit；hook 失败先调查，不使用 `--no-verify`。提交信息遵循项目约定。
- 推送当前 topic 分支到已核实的唯一实际 push URL，固定单一源/目标 refspec，不强推、不改默认目标分支。解析有效 push remote、pushurl 和 URL rewriting，不把 fetch URL 误当目的地。推送失败不创建 PR/MR。
- 自动模式通过实际 push URL 的远端 HEAD 解析默认目标，并把 PR/MR 的仓库身份绑定到同一目的地；不能可靠解析、目标等于源、现有开放 PR/MR 冲突或无法创建时停止并报告。支持可用的 GitHub PR / GitLab MR 宿主工具；不为此安装 CLI。重复运行时识别已有同源同目标的开放请求并报告，不创建重复请求。
- PR/MR 的标题和正文遵守目标仓库语言及模板约定；本插件仓库要求中文 Summary 和正文。正文如实记录审查、验证、未验证项与阻塞。创建 PR 后在支持的宿主读取当前状态；自动模式到此结束，不设置自动合并、不轮询 CI。

## 失败与验证

- 规范未初始化、项目规则写入权限不明、审查有未修复项、必要验证不足、暂存快照变化、远端不明、默认目标不明、受保护路径或无 PR/MR 能力时，在相应阶段停止，保留已有用户改动，并明确说明已完成和未完成的 Git 动作。
- 先写静态契约和压力场景的失败检查，再写技能。覆盖普通/自动分支、规范门禁、项目规则归属、暂存与推送边界、默认目标解析、PR 创建后停止及重复调用。运行聚焦测试和完整 `validate-plugin.ps1`；静态检查只证明文本契约，不宣称真实远端流程已执行。
