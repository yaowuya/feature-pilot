# fp-prd 业务逻辑优先设计

## 目标与依据

参考产品进化论 Lab 于 2026-08-28 发布的[《产品经理怎么写PRD？先把需求想清楚》](https://mp.weixin.qq.com/s/Ds7w1_LjBsGODrseCeaycg)，把 `fp-prd` 从容易产出页面操作说明的模板，增强为能解释业务如何运行的产品方案工作流。

2026-09-08 已通过浏览器读取正文；普通网页抓取遇到微信环境验证。采用正文中关于现状与目标流程、角色与系统影响、状态、规则、异常和后台不改依据的方法，不把文中提现示例当成所有产品的默认流程。

## 当前缺口

- 访谈已提及工作流和状态，但缺少先分析业务、再落页面的明确顺序与交付内容。
- 第二章示例以页面进入、点击、校验、刷新为中心，没有提示现状与目标差异、跨角色交接和业务结果。
- 功能交互缺少业务状态的进入/退出条件、执行责任、允许动作及结果可见性。
- `后台无需修改` 之类判断没有专门的证据要求。
- 访谈要求将超过五个的 Bucket C 决策降为 Bucket B，与不可代答高影响决策的原则冲突。

## 方案选择

采用**在既有结构内增强语义契约**，而非新增顶级章节或独立分析产物。

- 只加模板提示不能约束访谈和原型捷径，因此同时修改主技能、访谈技能和输出模板。
- 重做 PRD schema 或增加独立业务分析 skill 会增加用户负担及下游兼容成本，本次不采用。
- 访谈技能拥有业务分析顺序与决策分类；模板拥有具体内容落点和自检；主技能连接两者并管理写入门禁。

## 行为设计

### 1. 业务分析先于页面拆解

每次访谈先形成简短业务骨架：现状及依据、目标流程、变更点、参与角色/系统、业务状态与规则、异常闭环，之后才讨论页面表现。保留用户事实、当前源码证据、待确认产品决策和授权假设的区别。

新业务明确没有现存流程；简单文案/筛选变更以几条事实说明不改变业务状态即可。不得为了填满模板虚构后台、审核、支付或状态机。

### 2. 状态与规则必须可执行、可观察

对实际涉及持久业务状态的需求，记录状态、触发与前置条件、执行者、下一状态或结束条件、各角色可操作内容和结果可见位置。Loading/empty/error 等页面状态不能替代订单、申请等业务对象状态。

异常处理要说明业务停留/回退到什么状态，由谁重试、补救或处理，以及用户怎样看到最终结果；涉及业务风险的策略仍须确认。

### 3. 跨端不改也要有依据

确认受影响的用户端、运营/审核后台及外部系统，逐项说明变更、不变或不适用的原因。认定不变需要当前证据或用户提供的明确业务依据，至少能覆盖相关字段、状态、权限、处理流程和结果回显。缺证据时保留未知，不把 `估计不用改` 写成已验证事实，也不自行扩展为技术设计。

### 4. 访谈数量不是风险上限

3–5 个问题是沟通目标，而非完成配额。先问影响最大的依赖决策；超出的高风险问题继续逐个确认，或经用户明确缩小范围后移出本次范围，不因数量降级、不打包多问、不代答。没有阻塞问题时不凑问题。

### 5. 原型优先不等于页面等于业务

原型前只确认影响当前演示的业务骨架、规则和状态；其余业务问题保留到 PRD 前，不强迫先设计后台实现。原型通过只确认已演示的内容，不能证明后台可复用、资金处理正确或异常闭环已决定。

## 模板落点与兼容

- 第一章：用户价值、成功状态、MVP 与不做范围。
- 第二章：用加粗标签写现状流程、目标流程、变化与角色/系统影响；复杂流程仍用 Mermaid，简单功能说明无需图的理由。
- 第三章：`功能说明` 写业务规则，`交互逻辑` 写状态与责任及页面映射，`异常处理` 维持原表头并补充业务结果与补救责任。
- 第五章：原测试表中补充状态、角色交接、关键异常与不改链路回归的可观察结果。
- 第六章：只保留真正非阻塞的问题。
- 六个顶级章节、现有子标题、强制表头、四段 feature block、互斥 small/split 产物以及 `/fp-start <slug>` handoff 全部保持。

## 验证标准

1. 新的静态契约检查在旧技能上失败，在修改后通过；既有完整验证仍通过。
2. 运行旧技能压力场景，记录超过五个高影响决策时的实际分类，再用修改后的技能重测。
3. 提现页面改版必须产生业务层待确认问题，不能仅凭页面或一句后台不改进入完成状态。
4. 纯筛选/文案和绿地需求不得强制引入复杂状态或捏造现状。
5. 原型通过后仍能识别未决业务规则，不将 prototype acceptance 等同 PRD write approval。
6. 对状态/规则/异常覆盖进行人工语义复核；静态关键词检查不能声称证明运行时业务质量。

## 范围边界

仅维护仓库内技能、必要文档与测试。不执行产品 PRD 工作流、不改插件版本、不安装/同步本地运行时、不提交、不推送、不创建 PR。
