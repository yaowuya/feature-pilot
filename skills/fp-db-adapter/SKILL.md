# 信创数据库适配

自动识别项目现状和用户目标，规划并实施达梦、OceanBase 或两者的数据库适配。保留项目已有模式和迁移历史，不把静态推断描述为目标库验证结果。

## 不可跳过的两阶段门禁

每次任务都从阶段一开始。即使用户在首次请求中说“直接修改”或“自动执行”，也先完成扫描、输出方案并停止；只有用户看到当前完整方案后明确确认，才能进入阶段二。

### 阶段一：扫描与方案

- 只读取和分析项目、Git 状态及用户日志；不编辑、创建、删除或格式化项目文件。
- 自动判断适配类型、数据库范围和项目类型，并列出实际证据。
- 按 `references/adaptation-scope.md` 的固定检查分组和顺序逐项扫描；一次完成全部只读检查，不在分组之间请求确认。
- 内部为每项保留编号、固定状态、证据、判断依据和处置结论；默认输出按审批摘要压缩展示，不逐项复述全部扫描过程。
- 全部检查完成后汇总未适配项，输出文件级详细方案和总结，然后只请求一次统一确认并结束当前轮。

### 阶段二：实施与验证

- “确认”“按方案执行”“确认实施”等针对当前完整方案的明确授权，才可进入本阶段。
- 提问、补充日志、修改要求、只认可局部内容或首次请求中的预授权，均不视为确认。
- 只实施已确认的文件和数据库范围，并执行方案中的验证。
- 复用阶段一的检查项编号逐项实施和报告进度；不得修改标记为已适配或不适用的项目。
- 完成后输出实际修改总结、验证结果和未验证事项。

出现以下实质性方案漂移时，立即停止，输出补充方案并重新请求确认：

- 需要修改或新增当前方案未列出的项目文件。
- 需要删除外键、唯一约束、索引或其他业务约束。
- 需要修改已执行的原始 migration，而不是使用项目认可的补丁或后续 migration 机制。
- 需要改变数据库范围。
- 需要改变依赖主版本或替换数据库基础设施。
- 核心判断发生变化，导致实现方式或风险等级明显改变。

行号变化、格式化引起的位置移动，或同一代码锚点内不改变行为的小调整，不属于实质性漂移，但要在实施总结中说明。

## 自动判定

### 适配类型

判定为**全新适配**时，项目应整体缺少所选目标数据库能力，且任务是首次接入。综合检查：

- 是否缺少目标数据库的 `DATABASE_TYPE` 或 `DATABASES` 分支。
- 是否未注册 `cw_cornerstone.migrate_patch` 或项目等价机制。
- 是否不存在目标数据库迁移补丁目录。
- 是否缺少目标数据库 backend 或驱动依赖。
- 用户是否明确说明是新 SaaS、首次接入或从未适配。

出现任一强证据时，通常判定为**增量适配**：

- 已存在达梦或 OceanBase 配置、补丁机制或补丁文件。
- 用户提供已有适配后的 migration 或运行报错。
- 用户要求补充、修复、升级、完善或审查已有适配。

证据冲突时优先判定为增量适配，以保护已有实现和迁移历史。必须在方案中引用具体文件、配置或日志作为依据。仍无法可靠判断时，只询问一个能决定分支的关键问题，不把推断写成确定事实。

### 数据库范围

仅支持以下范围：

- `dameng`：仅达梦。
- `oceanbase`：仅 OceanBase。
- `all`：达梦 + OceanBase，即本技能所称“全量数据库”。

按以下优先级判断：

1. 用户明确指定的数据库范围优先。
2. 报错日志明确来自一个数据库时，默认仅处理该数据库。
3. 用户说“全量适配”“全部适配”或“全库适配”时，范围为 `all`。
4. 用户只说“信创适配”且未指定范围时，根据项目缺口提出推荐：两者都缺失时推荐 `all`；仅缺一方时推荐缺失的一方；已有双方能力时根据实际问题确定。

推断或推荐的范围必须写入方案并等待确认，不能视为已经获得实施授权。不得自动扩展到人大金仓、瀚高、GaussDB 等未支持数据库。

## 扫描与参考路由

- 全新或增量适配审计时，读取 `references/adaptation-scope.md`。
- 涉及 migration 扫描、报错或补丁时，读取 `references/compatibility-checklist.md`。
- 仅在代码或用户信息确认项目是 AutoOps、蓝鲸 SaaS，或采用同类 `cw_cornerstone` 约定时，读取 `references/autoops-patterns.md`。普通 Django 项目不得套用其中固定版本、配置路径和平台变量。
- 日志不完整时，先说明缺失信息；仍可静态定位，但将结论标为“基于静态推断”。

## 固定检查状态

每个检查项只能使用以下状态之一。内部检查记录不得省略已适配或不适用的项目，默认方案按分组合并展示：

- `[已适配，跳过]`：有充分证据证明目标能力已适配，明确输出“<检查项> 已适配，跳过”。
- `[需要适配]`：确认能力缺失或当前实现不兼容，纳入适配方案。
- `[待验证]`：静态扫描无法证明兼容或风险较高，纳入验证方案。
- `[不适用，跳过]`：不属于当前项目、适配类型或数据库范围，说明原因后跳过。
- `[无法判断]`：缺少必要代码、配置或环境信息，列出需要补充的内容。

不能仅凭文件名、注释、目录存在或依赖声明判定为已适配。必须引用能证明实际注册、配置、执行路径或验证结果的证据；证据不足时使用 `[待验证]` 或 `[无法判断]`。

每个检查项的内部记录至少包含：

- 检查项编号和名称。
- 固定状态及明确结论。
- 文件路径和扫描时的当前行号（存在文件证据时）。
- 稳定代码锚点（存在代码证据时）。
- 判断依据或扫描发现。
- 后续处置：跳过、纳入适配方案、纳入验证方案或等待补充信息。

## 阶段一输出契约

默认方案以审批决策为中心，严格使用以下七个一级标题和顺序。不要输出冗长的搜索过程；一个事实只完整说明一次，其他位置使用适配编号引用。

### 1. 适配分组概览

在方案最前面使用固定表头列出 `references/adaptation-scope.md` 的全部十个检查分组，让用户先看到完整适配范围：

| 分组 | 简要说明 | 本次检查范围 |
| --- | --- | --- |

十个分组及简要说明固定为：

| 分组 | 简要说明 |
| --- | --- |
| 1. 项目与适配模式识别 | 识别项目类型、全新或增量适配、目标数据库及验证条件 |
| 2. Python 及系统依赖 | 检查 Python、Django、`cw-cornerstone`、数据库驱动和构建依赖 |
| 3. 数据库驱动与后端适配 | 检查达梦与 OceanBase backend 的可用性、注册和能力覆盖 |
| 4. 数据库连接配置 | 检查数据库路由、连接参数、环境变量和默认字段策略 |
| 5. Migration 兼容机制 | 检查补丁注册、数据库补丁路由、覆盖规则和历史保护 |
| 6. 现有 Migration 文件 | 检查字段类型、DDL 顺序、数据迁移、第三方迁移和上线风险 |
| 7. ORM 查询与原生 SQL | 检查 ORM 特殊行为、批处理及数据库专属 SQL 兼容性 |
| 8. 初始化、升级及运维脚本 | 检查初始化、升级、数据导入导出、运维脚本和幂等性 |
| 9. 部署、镜像与环境配置 | 检查部署描述、镜像依赖、服务绑定、变量注入和发布顺序 |
| 10. 测试和验证能力 | 检查静态验证、migration 计划、目标库实连和回归测试条件 |

“本次检查范围”简要写明 `达梦`、`OceanBase`、`两者` 或 `不适用但仍检查并标记跳过`，不得在概览中展开检查结果、证据、路径或改动内容。

### 2. 适配结论

使用紧凑表格展示适配类型、数据库范围、需要适配数量、待验证数量、计划修改文件数、风险等级和当前状态。项目类型可作为附加行。判断依据只保留一至三条最关键事实，不在本节罗列全部证据。

### 3. 适配列表

只列出需要用户关注的项目，使用固定表头：

| 编号 | 适配内容 | 数据库 | 文件位置 | 处理方式 |
| --- | --- | --- | --- | --- |

编号规则：

- `A1`、`A2`：确认需要修改，用户确认后实施。
- `V1`、`V2`：需要验证后决定或只需验证，按方案执行验证。
- `Q1`、`Q2`：缺少关键信息，信息补齐前不实施。

文件位置可合并多个直接相关文件，但不得隐藏计划修改文件。每个列表项都必须在“改动明细”中有同编号内容。

### 4. 已适配与跳过

使用 `| 分组 | 结果 |` 短表格。同组多个已适配项合并成一句，并保留“已适配，跳过”；不适用内容用一句话说明原因。默认不重复路径、行号、锚点或代码块，但不得隐藏 `[需要适配]`、`[待验证]` 或 `[无法判断]` 项。

内部仍严格完成 `references/adaptation-scope.md` 的十组检查。仅在用户要求完整审计，或存在已适配结论争议、证据冲突、高风险、无法判断、可能影响确认的省略证据时，在本节后增加“完整检查明细”，表头固定为：

| 分组 | 检查内容 | 状态 | 结论 | 证据位置 |
| --- | --- | --- | --- | --- |

### 5. 改动明细

只展开 `A`、`V` 和 `Q` 项，每项使用 `### A1 适配内容` 格式，并包含：

- 原因和目标数据库。
- 文件路径、修改类型、当前行号和稳定代码锚点；新文件写“预计从第 1 行开始”。
- 当前代码或状态，以及计划代码或处理逻辑；只展示最小相关代码块。
- 行为影响、风险、验证方式、执行顺序和前后依赖。

同一文件涉及多个项目时合并共同背景，保留每个编号和独立结果，避免重复代码。`V` 项明确“只验证”或“验证失败后输出补充方案”；后者不得预先修改。存在 migration 改动时，说明原 migration、补丁路径、兼容问题、`dependencies`、operation、执行历史、回滚、幂等、数据量和锁表风险。

### 6. 执行与验证

使用简短编号列表说明适配项实施顺序、达梦验证、OceanBase 验证和当前无法执行的验证及原因。区分语法/Django 检查、migration graph/plan、目标库实连和核心业务读写；适配 `all` 时分别列出两种数据库，不用一方结果代替另一方。

### 7. 方案汇总与确认

只汇总需要适配、待验证、无法判断、已适配并跳过、不适用并跳过、计划修改文件数量，并明确“当前未修改任何项目文件”和“状态：等待用户确认方案”。

若 `Q` 项缺失的信息会影响方案正确性或实施范围，先请求补充信息，不得请求实施确认。信息完整时，请求用户对完整方案确认、调整或取消。输出后停止，不重复前文，也不在同一轮进入实施。

## 阶段二输出契约

严格复用已确认适配列表的编号和顺序，逐项输出以下适用状态，不得只说“实施完成”或“部分失败”：

- `[A1 实施中]`、`[A1 成功]`、`[A1 失败]`、`[A1 跳过]`。
- `[V1 验证中]`、`[V1 验证通过]`、`[V1 验证失败]`。

每个成功项目立即说明实际修改的文件和位置、实际适配的配置/代码/Migration/依赖、该项验证结果，以及与确认方案是否一致。

每个失败项目立即说明失败步骤、原始错误或准确失败原因的简明摘要、已产生修改及其状态、对后续项目的影响，以及下一步是继续、跳过依赖项、输出补充方案还是等待信息。失败不代表自动回滚用户已有改动；若失败导致实质方案漂移，停止相关后续项目并重新确认，独立项目按已确认的依赖关系决定是否继续。

实施完成后输出两张紧凑表格：

| 编号 | 适配项 | 结果 | 实际适配内容或失败原因 |
| --- | --- | --- | --- |

| 文件 | 对应编号 | 实际改动 | 验证结果 |
| --- | --- | --- | --- |

随后汇总成功、失败、跳过和待处理数量，分别给出达梦与 OceanBase 的验证结论，并说明：

- 最终适配类型和数据库范围。
- 实际修改及新建文件，以及修改后的真实行号和稳定代码锚点。
- 每个 migration 命中的适配点。
- 方案与实际实施的差异；无差异时明确说明。
- 已执行的验证命令和逐项结果。
- 静态验证与目标库实连验证的区别；没有真实目标库时写明“未做目标库实连验证”。
- 未验证事项、遗留风险和上线注意事项。

实施期间即时报告，例如：

```text
[A2 实施中] OceanBase 数据库后端配置
[A2 成功] OceanBase 数据库后端配置
[V1 验证失败] 达梦长文本批量写入
```

最终总结将每个已确认计划项映射到实际变更及验证结果。

不得将静态检查、migrate plan 或代码审查描述为目标数据库实连通过。
