# 工程质量契约：可读代码与适度设计

在技术设计、任务规划、代码实现/修复、设计评审或代码 review 前读取一次。本文件是注释、复杂度和有意简化的唯一规则来源；只读探索和纯产品需求讨论无需加载。控制器必须把解析后的本文件路径传给独立 implementer、fixer 和 reviewer，不能依赖它们继承会话。

## 适用范围

- 必须覆盖本次新增代码和本次改变行为的对象；修改行为时同步修正已有注释。范围外旧代码不触发全库补注释或重构。
- 注释语种与格式遵循目标项目明确约定和邻近代码；没有约定时使用团队可读的中文，保留必要技术标识符。Python/Django 细则仅在对应技术栈启用，不要求其他项目引入这些框架或分层。
- 使用已有 docstring/lint/格式约定。不得为了本契约安装新的检查器、引入依赖、修改 CI 或创建独立文档体系。注释数量与覆盖率不是验收指标。

## 写代码时同步写说明

1. 新增业务模块、公开类/函数/方法，以及本次改变行为的公开对象，必须有准确的职责与契约说明。Python 使用 docstring；其他语言使用现有项目的文档注释形式。说明用途，并按需补充输入限制、返回语义、异常、副作用和调用前提，不复述签名与类型。已有说明准确且充分时保留即可。
2. 非显然的业务规则、权限/租户隔离、事务/锁/幂等边界、特殊查询、兼容分支、外部协议限制及性能取舍，必须在对应实现附近解释原因、约束或不变量；私有辅助函数也适用。单纯命名或外部设计文档不能替代这里的解释。
3. 一句能说清的就用一句。显然的赋值、循环、字段、简单私有 helper 不逐行翻译；空泛的“处理数据”、签名复述、无事实依据的保证、失效注释和占位 TODO 都不合格。测试说明应描述预期行为和边界。
4. 文档/注释不能掩盖实现缺陷；运行行为、注释、测试必须一致。修改后连同附近现有说明一起检查，而不是只给新增行加 `#`。

### Python / Django 条件细则

Python 的 docstring 按 PEP 257 写简短摘要，确有必要时空行后补细节；遵循已有项目风格。以下是 FeaturePilot 参考官方文档制定的交付要求，不宣称 Django 官方要求每行、每字段都有注释。

| 实际变更对象 | 必须说明的内容 |
| --- | --- |
| Model、Manager、QuerySet 与自定义方法 | 领域职责；非显然的业务不变量、过滤范围和自定义保存/查询语义；约束为何存在。 |
| 有特殊语义的字段 | 单位、时区、状态编码、空值含义等无法由名称/类型直接看出的语义。简单字段无需重复说明。 |
| View、Form，以及项目已有的 Serializer/Service | 入口职责；适用的输入/权限约束、错误和写入副作用。仅使用项目已有分层，不为写注释新建 service/repository 层。 |
| 事务、锁与外部副作用 | 原子边界、锁与幂等的原因，提交后动作及失败语义；注释必须与实际保证一致。 |
| 手写数据 migration、RunPython、RunSQL | 变换目的、数据假设、可逆性或不可逆原因，以及重要批次/锁影响；数据迁移按框架要求使用历史模型。 |

`verbose_name`、`help_text`、`db_comment` 有展示或数据库用途，不能替代源码解释。不得仅为“有注释”添加这些属性、改变用户界面或制造 schema migration。纯自动生成的声明式 migration、空 `__init__.py`、生成代码及第三方文件不为达注释数量机械改写；自定义数据变换仍须说明。

## 设计先满足当前需求

1. 先给出满足已确认需求、正确性和运行约束的最简单可行方案，优先复用现有代码、项目惯例与框架能力。复杂度取舍写在现有架构决策或主线中，不增加独立设计产物。
2. 每个新增抽象、层、通用接口、依赖、配置开关、缓存或异步机制，必须能指出它现在解决的具体需求/故障、实际复用差异或已验证瓶颈，并说明直接实现为何不足。只有一个实现时不默认配套 factory、registry、plugin system 或通用基类；“以后可能用到”不是充分依据。
3. 分层、缓存和扩展点有当前证据时可以采用，不能为了少写代码破坏已有边界。比较真实可行的方案及维护成本，不堆砌假想选项，也不把全部可选能力默认实现。
4. 简化必须保留本次已承诺的功能、验收、权限/隔离、安全、数据完整性、一致性、兼容、迁移/回滚和必要验证。遗漏这些要求是缺陷，不能用技术债注释使其合格。
5. 规划与执行沿用已确认选择；发现需要改变行为、接口、架构或验收的“简化”时，返回已有决策流程，不能在实现中擅自削减设计。

## 有意延后须可追踪

借鉴 ponytail-debt 的做法，仅对确有取舍的临时简化记录上限与升级条件。正常的简单实现不是技术债，不为每个函数制造标记。

- 设计阶段在已有决策/风险 owner 中记录：简化内容与当前理由、适用上限、可验证的重访触发条件、升级方向；无延后项时写“无”。不虚构容量数字或把“以后优化”当触发条件。
- 实现阶段在对应代码附近使用项目既有债务标记；项目没有约定时用 `fp-debt:`，已有 `ponytail:` 也可直接保留。正文包含同样的理由、上限、触发条件和升级方向，并链接已存在的设计/issue（若有）。文档引用不能替代关键内容。

示例（只表示注释结构，不替项目决定业务边界）：

```python
# fp-debt: 当前导出仅覆盖已批准的单租户有界数据集，因此沿用同步导出。
# 上限：现有导出范围与请求时限；触发：加入跨租户批量导出，或实测超出请求时限。
# 升级：改为后台导出任务，沿用租户权限与结果访问校验。
```

- reviewer 只扫描本次 diff、受影响对象及其直接相关的既有标记，排除依赖、生成/构建目录和单纯提及约定的文档。核对上限是否仍成立、触发条件是否已达到，缺少触发条件或升级方向记为 `no-trigger`，要求补齐实际依据。
- 在现有自审/执行报告/review 风险项内汇总 `path:line`、简化内容、上限、触发条件、升级方向及处置；无需新增技术债文件、命令或全库扫描。代码标记是事实源，报告引用它，避免维护第二份台账。
- 有意延后不等同于 SDD 的 `Review Debt`，不能用标记绕过原有阻塞项和 review 次数上限。

## 完成前的强制检查

执行者在提交或勾选任务前、reviewer 在给出结论前，对照实际 diff 检查：

- 新增/改变行为的公开对象有准确的契约说明，非显然逻辑有原因注释，附近旧说明已同步。
- 新复杂度有当前依据，实际实现符合已确认的简单方案。
- 有意延后的代码标记信息完整，当前仍处于有效边界内，已触发的升级已处理或回到决策流程。

执行者必须先修复缺失/失效/误导说明或无依据复杂度，才可声明完成。reviewer 在现有 Findings 中给出 `path:line`、具体缺失及阅读/正确性影响；本次代码违反上述必须项时至少记为 Important / 对应阻塞级别，不能批准、勾选完成或降为 `Review Debt`。只剩措辞优化时可按现有 Minor 规则处理；未触及旧代码的文档建议不自动升级成强制改造。无法检查时如实报告未验证，不能仅凭测试通过认定本契约通过。沿用当前流程的重试与阻塞处理，不增加新状态机。

## 参考依据

- [Django coding style](https://docs.djangoproject.com/en/6.0/internals/contributing/writing-code/coding-style/#python-style)：Django 自身贡献规范，参考 PEP 8、PEP 257 与邻近代码风格。
- [PEP 8 — Comments / Documentation Strings](https://peps.python.org/pep-0008/#comments) 与 [PEP 257](https://peps.python.org/pep-0257/#specification)：注释准确性、公开接口文档、摘要与必要契约信息。
- [Django model fields](https://docs.djangoproject.com/en/6.0/ref/models/fields/)、[transactions](https://docs.djangoproject.com/en/6.0/topics/db/transactions/#performing-actions-after-commit)、[historical models](https://docs.djangoproject.com/en/6.0/topics/migrations/#historical-models)：字段元数据、事务与迁移机制；这里的强制说明要求由 FeaturePilot 制定。
- [ponytail-debt](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail-debt/SKILL.md)：让有意简化的上限、升级路径与重访条件留在代码旁，并在 review 中识别缺少触发条件的条目。
